# Xosvi 排障方法论（证据驱动，不靠猜）

> 这份文件把「找问题为什么准」拆成可复用的步骤。任何一轮修 bug、看用户报障、
> 判断某个功能到底能不能用，都按这里走。和 `AGENTS.md` 的硬约束配合使用。

## 0. 三条底线（照 `AGENTS.md`，这里只强化执行）

1. **区分「已查证 / 推断 / 未验证」**，三者不许混说。代码改了但没在设备上跑过，只能说「已改，未验证」。
2. **同一工具 + 同一参数 + 同一类错误连续 2 次即停**，换证据来源，不硬撞。
3. **破坏性操作先备份**，结果里给出备份绝对路径。

## 1. 先把现象变成可验证的事实

用户说的是「现象」，不是「原因」。拿到报障后第一件事是**找一条能直接验证的数字或文件**：

| 用户描述 | 不是去猜 | 而是去找 |
|---|---|---|
| 「检测镜像全部超时」 | 网络不好 / 权限不够 | 测速请求的实际 URL、`curl -I` 的返回码 |
| 「工具装不上」 | iSH 坏了 | 根文件系统里 `lib/apk/db/installed` 到底有几个包 |
| 「模型连不上」 | 密钥错了 | 请求体、endpoint 路径、`/models` 能不能列 |
| 「界面卡住」 | 逻辑死锁 | 日志里的最后一行、耗时字段 |

**判据：能不能给出一个路径、一个数字、一段日志。给不出，就还没开始。**

## 2. 把事实对回代码

有了事实，去代码里找**产生这条事实的那一行**：URL 是拼出来的、路径是写死的、参数是默认的。
对上了，因果链才成立；对不上，说明还有第二处，别急着修。

## 3. 同类扫描：一个坑往往有两处

改之前先搜一遍同类写法：

- 写死的架构名（`aarch64` vs iSH 的 `x86`）
- 写死的源地址（`repositories`、镜像、endpoint）
- 用默认值当业务值的地方
- 异常被吞成「空列表 / 空字符串」

```sh
grep -rn 'aarch64' Sources/
grep -rn 'repositories' Sources/
```

**经验：第二轮扫描通常会再抓出 1–2 条第一轮漏掉的同类问题。** 这一步不能省。

## 4. 边界与陷阱优先于「失败重试」

很多「偶发失败」其实是稳定边界，先查已知坑清单（`AGENTS.md` 的「环境与桥接」）：

- iSH 只走 `http://`，`https` 握手会挂死 → 报「超时」时要先排除这个
- `apk` 残留 `/lib/apk/db/lock` → 表现为「一直在转」
- iOS 原生 shell 不做通配符展开、不支持相对路径、二进制 `grep` 不可靠
- spawn 失败先看 `errno`：2 / 8 / 13 都不是「被越狱拦」，只有 85 才是

## 5. 修完必须闭环验证

| 修的东西 | 最小验证 | 做不到时的说法 |
|---|---|---|
| 网络/接口 | 真发一次请求，看返回码与字段 | 「已改，未发请求验证」 |
| 安装类 | 真跑一次安装，`installed` 里能看到包 | 「已改，未实际安装」 |
| UI 布局 | 设备截图 / 元素树读数 | 「已改，未看效果」 |
| 启动/守护 | 进程状态 + 日志标记 | 「已改，未确认加载」 |

**没有验证就不许说「好了」。** 说「已改，等你装上看效果」，比含糊的「修好了」有价值得多。

## 6. 回写

- 每轮发现的**新坑**补进 `AGENTS.md` 的对应小节（尤其是环境类）。
- 每轮修掉的**根因**写进 commit message 的正文，便于下次 grep。
- 结论先给判断，再给证据：命令 / 路径 / 字节 / 哈希 / 表结构。

## 7. 案例库（已查证 + 可复现）

### 案例 1：控制台「注入 → 闪退」（EXC_GUARD / namespace LIBXPC / XPC_EXIT_REASON_FAULT）

- **现象**：`control inject` 选完目标后 App 直接闪退；审计日志无记录（崩溃前不写）。偶发，
  同一个按钮有时只报通道错误不崩。
- **事实**：崩溃原因里出现 `EXC_GUARD`、`namespc 7`、`subtype LIBXPC`、`reason 9`，
  即 libxpc 自己的「误用」出口，不是业务代码的野指针。
- **对回代码**：`Sources/XosviMCP/XosviXPC.swift` 的 `request` 把
  `xpc_connection_send_message_with_reply` 回调参数存进 `Box`，等主线程 `sem.wait`
  回来才 `replyDict(对象)`。reply 对象只在块执行期间有效，块返回后 libxpc 已回收。
- **复现**：`tools/xpc-reply-lifetime.c`（编译+`ldid -S` 后跑）
  - `bad` 模式（块外读）：`Trace/BPT trap: 5` / `Bus error: 10`，必崩；
  - `good` 模式（块内解析）：`status=OK uid=0 (parsed inside the reply block)`；
  - 把服务名换成不存在的（`good wiki.qaq.nonexistent.svc`）得到 `status=(no status)`，
    说明「有 status 才证明真收到守护回复」，别把错误对象读出来的 `0` 当结果。
- **结论**：**xpc 对象不能跨块存活**。要跨块就把值读成 Swift 类型带走
  （字符串 / 整数 / `Data`），或显式 `xpc_retain` 后再配对的 `xpc_release`。
- **顺带纠正**：本机 XPC 通道一直是通的（`status` 返回 9 键字典、`helper` 以 uid=0 执行、
  `exit_code=0`）。此前「本机对任何 MachService 都 Connection invalid」的说法源于两处误读：
  守护回复后取消连接本就产生一次 `Connection invalid` 事件；以及上面这处 use-after-free。
